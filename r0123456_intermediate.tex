\section{A basic evolutionary algorithm \hfill(target: $1$ page)} 

\subsection{Representation}

Permutation representation is a natural choice for the TSP problem, as it directly encodes the order in which cities are visited. 
Each tour is represented by an array of cities. For example, a candidate solution [0, 2, 1, 3] represents a tour that starts at city 0, then visits city 2, followed by city 1, and finally city 3 before returning to the starting point.
This format makes it easy to create, modify, and evaluate different
tours.
We chose to use NumPy arrays because they store data efficiently and allow fast operations, which is important
when working with large populations in evolutionary algorithms. Other options, like sets, lists, and maps, were
considered but had drawbacks. Sets dont keep items in order, so they wouldnt work well for representing tours.
Maps were more complex than needed since they require key-value pairs, adding unnecessary overhead. Lists
are similar to arrays but arent as fast in numerical operations as NumPy arrays, which made arrays the better
choice

\subsection{Initialization}

The population is initialized by generating random permutations of the city nodes, ensuring that each candidate
solution represents a feasible tour. In each iteration, a random tour is created by shuffling the list of nodes. After
generating each tour, the algorithm checks that the total cost of the tour is not infinite. This ensures that all initial
solutions are valid and avoids routes that can’t be completed due to nodes that are not connected.

Practicall, this is done using Python's built-in `random.sample` function, which creates a random permutation of the cities without repetition. 
This way, every individual in the initial population might represent a different tour.

\subsection{Selection operators}


For selection, we used tournament selection, which helps pick good solutions but also keeps some diversity in the population balancing exploration and exploitation effectively.
In this method, a subset of individuals is randomly chosen from the population, and the one with the best fitness (lowest cost) in that 
group is selected as a parent for reproduction. This is repeated until we have enough parents for crossover.
This method helps maintain diversity in the population while still favoring fitter individuals.

\noindent Tournament selection allows stronger solutions to be chosen more often but still gives weaker solutions a chance, which keeps 
diversity and helps avoid getting stuck in local optima. The main settings for this method are \texttt{TOURNAMENT\_SIZE} and \texttt{SELECTION\_SIZE}. 
We set \texttt{TOURNAMENT\_SIZE} to 5, which provides a balance by favoring better solutions without being too selective. 
\texttt{SELECTION\_SIZE} is set to 75, which means we select 75 parents for crossover. 
This setup keeps a good mix of solutions for each generation and helps the algorithm to converge without losing diversity.

\subsection{Mutation operator}



For mutation, we implemented a simple swap mutation. 
This involves selecting two random cities in the tour and swapping them. This small change introduces randomness, which helps the algorithm 
explore new solutions.

\noindent The mutation rate is controlled by the parameter \texttt{MUTATION\_RATE}, which we set to 0.05. 
This means each individual has a 5\% chance of mutation. A low mutation rate helps maintain stability in the population by making small changes, 
but it still allows enough variety to avoid early convergence. This setup helps the algorithm to gradually improve solutions without losing good 
features in the population.


\subsection{Recombination operator}


For recombination, we used "Order Crossover". This method creates offspring by combining parts of two parent tours while preserving the 
relative order of the cities. In this method, a segment from one parent is copied to the offspring, and then the remaining cities from the other 
parent are filled in while keeping their original order.

\noindent We chose this method because it is effective for problems where the sequence of entities matters. It ensures that offspring inherits 
good traits from both parents while still allowing for the exploration of new solutions.

\noindent The crossover is controlled by the \texttt{CROSSOVER\_RATE}, which we set to 0.7. This means there is a 70\% chance that crossover 
will occur when generating offspring. This rate strikes a balance between exploring new combinations and preserving high-quality solutions, 
helping the algorithm to converge effectively while maintaining diversity in the population.

\subsection{Elimination operators}
For elimination, we chose tournament selection again to reduce the population after generating new offspring. 
After creating the new individuals through crossover and mutation, we combine them with the existing population and then 
select the best individuals to form the new generation.

\noindent The elimination process involves evaluating the fitness of all individuals in the combined population and then running another 
tournament selection to pick the fittest candidates based on the \texttt{TOURNAMENT\_SIZE} and  \texttt{POPULATION\_SIZE} parameters. 
By setting \texttt{POPULATION\_SIZE} to 100, we ensure that only the top 100 individuals are kept for the next generation. 

\noindent This method allows the algorithm to build on good solutions while still keeping some diversity, preventing early convergence. 
By continuously selecting the best individuals, we can effectively drive the evolution of the population toward an optimal solution over time.

\subsection{Stopping criterion}


The algorithm stops running based on two main conditions: a time limit and a check for improvement in the best solution.

\noindent The first condition is the build-in time limit. The algorithm continuously checks how much time is left to run by using the built-in 
reporter function. When the remaining time is less than zero, the algorithm automatically stops. This keeps the algorithm from running indefinitely 
and ensures it completes within the allowed time.

\noindent The second condition stops the algorithm if there has been no improvement in the best solution’s cost over a certain number of 
generations (defined by \texttt{CONVERGENCE\_PATIENCE}). If the best solution doesn’t improve after this many generations, the algorithm assumes 
it has “converged” and stops, as it is unlikely to find better results by continuing.

\noindent Together, these conditions allow the algorithm to stop either when it reaches a time limit or when it has stabilized at a good solution, 
thus saving resources while still allowing it to search for an optimal solution.

The core idea during the code generation phase was to decompose the implementation into modular components and prompt the LLM to generate each component individually. Additionally, to improve correctness and maintainability of the generated code, we employed step-by-step (chain-of-thought) prompting over multiple iterations. This strategy resulted in more precise prompts, better controllability, and a clearer structure in the final codebase.
\\\\
We first defined the representation of the Traveling Salesman Problem (TSP) ourselves. After that, we generated each component of the evolutionary algorithm by providing the function signature (function name, input specification, and required output). Below is an example of the prompting process used for generating the selection operator:

\begin{dialogue}
  \speak{Prompt 1}
    I want to create a selection operator for a genetic algorithm of the Travelings Salesman problem. The representation of the problem is already defined: a (permutation) list that represents the order of the visited cities. Which are the options and what are advantages and disadvantages?
  \speak{Effect on LLM}
    This ensures that the LLM “understands” the problem setup and has sufficient context to design a suitable selection operator. At the same time, it provides an overview of candidate approaches and their trade-offs.
  \speak{Prompt 2}
    I want you to implement k-tournament selection for a population of individuals in a genetic algorithm for the Travelings Salesman problem. Each individual is represented as a permutation list of cities. The function should take as input a list of individuals and an integer k, representing the number of individuals to select for the tournament. The function should return the selected individual from the tournament. To guide you, I already defined an Individual class that has a fitness attribute. You can use this information, together with the function header below, to implement the k-tournament selection.
    \begin{python}

    \end{python}
\end{dialogue}

\subsection{Prompts to fix errors}
%\ReplaceMe{Was the generated code free of errors? If not, what was wrong? What type of errors were they: misinterpretation, logical, or programming errors? How did you instruct Copilot to fix these errors? Record the prompts. Did you apply some postprocessing? What did you do?}
While the generated code was generally functional, several minor corrections were necessary during integration into our codebase. The most notable issue was a misalignment with our predefined data structures: the Individual class internally stores the tour as a \texttt{np.ndarray}, but the LLM initially implemented the order as a standard Python list. This inconsistency caused type mismatches when combining operators and computing distances. To resolve this, we provided a corrective follow-up prompt, asking the LLM to update the previously generated code accordingly:

\begin{dialogue}
  \speak{Prompt}
    You implemented the partially mapped crossover operator correctly, without any errors. However, there is a small issue: the order of an individual is implemented as a normal python array, while it should be a numpy array (np.ndarray). Please fix this in the code you generated before.
\end{dialogue}

\noindent
After receiving the updated response, we verified that all operators produced consistent data structures and made a few additional adjustments such as renaming variables for readability and refining comments. Overall, postprocessing primarily involved ensuring internal consistency rather than modifying core logic.

Generative AI excels at brainstorming and generating ideas, particularly when domain knowledge is limited. It can help get started quickly and provide a foundational implementation to build upon. However, effective use requires a solid understanding of the problem and underlying concepts, in order to guide the AI and critically evaluate its output. In this sense, prompt engineering becomes as important as traditional coding skills. While LLMs can accelerate the initial coding phase, they may also increase the time needed for reviewing, debugging, and integrating larger blocks of code. Furthermore, the AI does not always self-correct, so careful verification remains necessary. Given the rapid progress of LLMs in recent years, it has however become essential to at least learn how to work with them and understand what to realistically expect from their outputs. Ultimately, the developer's expertise and the trade-off between development speed and code quality determine the most effective way to leverage generative AI in a project.
