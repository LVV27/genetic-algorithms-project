\subsection{Representation}\label{sec_rep}

\ReplaceMe{How do you represent the candidate solutions? What is your motivation to choose this one? What other options did you consider? How did you implement this specifically in Python (e.g., a list, set, numpy array, etc)?}

Candidate solutions are represented as a \textbf{permutation} of the city indices, i.e.\ a tour
$\pi = (\pi_1,\dots,\pi_n)$ that visits each city exactly once. The objective value is the total length of the
Hamiltonian cycle induced by this permutation (including the return edge to the first city).

This representation was chosen because it is the \textbf{natural encoding} for the TSP, guarantees feasibility
(no duplicated/missing cities) when using permutation-aware operators (e.g.\ OX crossover and inversion-based
mutations), and allows efficient evaluation and local search (2-opt acts directly on segments of the permutation).
Alternatives considered were an \textbf{adjacency / successor representation} ($\text{succ}[i]=j$) and
\textbf{edge-set encodings}; these can simplify overlap/diversity calculations but make crossover and repair
more involved.

In Python, each tour is stored as a \texttt{numpy.ndarray} of integers (attribute \texttt{Individual.tour}),
which enables fast slicing/reversal (used by inversion mutation and 2-opt) and supports Numba-accelerated fitness
evaluation. The deterministic crowding diversity measure additionally builds a temporary successor array
\texttt{succ} from the permutation for fast directed edge-overlap computation.


\subsection{Initialization}

The initial population is created using a \textbf{mixed strategy}: a small fraction
($\lfloor \texttt{GREEDY\_FRACTION}\cdot \lambda \rfloor$) is generated with a \textbf{nearest-neighbour greedy}
heuristic from multiple random start cities, and the remaining individuals are \textbf{uniformly random
	permutations}. All candidates are evaluated immediately and only tours with finite fitness are kept.

The population size was set to $\lambda=100$ after empirical tuning: larger populations increased runtime and
reduced the number of generations within the time limit, while smaller populations converged prematurely. The
greedy component is intentionally capped to a very small fraction (default $\texttt{GREEDY\_FRACTION}=0.01$),
so enrichment provides \emph{good building blocks} without taking over the population; the bulk of the
population remains random, which maintains diversity from the start.

Parent selection is performed using \textbf{$k$-tournament selection}: for each parent, $k$ individuals are
sampled uniformly at random from the current population and the individual with the lowest fitness is selected.
This operator was chosen because it is simple, efficient, and provides a controllable trade-off between
selection pressure and diversity.

The main parameter is the tournament size $k$ (set to $k=5$). Larger $k$ increases selection pressure and
accelerates convergence but risks premature convergence; smaller $k$ preserves diversity but slows progress.
In the final version, $k$ is kept constant (no dynamic schedule).

\subsection{Mutation operators}

We use a \textbf{mutation portfolio} for permutation tours: \textit{swap} (exchange two cities), \textit{inversion}
(reverse a contiguous segment), and \textit{insertion} (remove one city and insert it elsewhere). If mutation is
triggered, the operator is chosen by a \textbf{weighted roulette} (in the final version: inversion is preferred,
as it typically performs better for the TSP, while swap/insertion provide additional perturbations).

Randomness is controlled by an \textbf{individual-specific mutation rate} $\alpha$:
mutation is applied with probability $\alpha$, where $\alpha \sim U[\alpha_{\min},\alpha_{\max}]$ at
initialization. The rate is then inherited by offspring (i.e.\ a simple self-adaptive parameter), so different
lineages can maintain different exploration levels. We do not use a generation-dependent schedule for $\alpha$.

Recombination is performed with \textbf{Order Crossover (OX)} for permutation encodings. OX copies a random
contiguous segment from the first parent and then fills the remaining positions by scanning the second parent in
order and inserting the cities that are not yet present. This preserves \textbf{relative order information} from
the second parent while keeping a block (subtour fragment) from the first parent.

We use a single recombination operator (no operator portfolio); crossover is applied with probability
$p_c$ (final setting: $p_c=1$) and otherwise the first parent is cloned. The segment boundaries are sampled
uniformly at random, which controls how disruptive the crossover is (short segments $\rightarrow$ more parent-2
order preserved; long segments $\rightarrow$ more parent-1 block preserved). No self-adaptivity or
generation-dependent schedule is used for $p_c$.

\subsection{Elimination operators}

\ReplaceMe{Which elimination operators did you implement? If they are not from the slides, describe them. Why did you select this one? Are there parameters that need to be chosen? Did you use an advanced scheme to vary these parameters throughout the iterations? Did you try other elimination operators not included in the final version? Why did you discard them?} 

Survivor selection uses \textbf{deterministic crowding}. After generating offspring, each child competes with the
\emph{most similar} individual in the current population (its ``rival'') and replaces it only if it has better
fitness. Similarity is measured by \textbf{directed edge overlap} using a successor representation
($\mathrm{succ}[i] =$ next city), i.e.\ the number of matching directed edges. Ties are broken by choosing the
closest fitness.

This elimination operator was selected to \textbf{preserve diversity} and reduce premature convergence, while
still enforcing progress through local competition rather than global truncation. It has no critical continuous
hyperparameters in our implementation; the main design choice is the similarity metric (edge overlap). We do not
vary elimination settings over time.

We also used standard \textbf{($\lambda+\mu$) truncation} earlier (keep best individuals from parents+offspring),
but it increased selection pressure too much and reduced diversity, so deterministic crowding was preferred in
the final version.

\subsection{Local search operators}

\ReplaceMe{What local search operators did you implement? Describe them. Did they cause a significant improvement in the performance of your algorithm? Why (not)? Did you consider other local search operators that did not make the cut? Why did you discard them? Are there parameters that need to be determined in your operator? Do you use an advanced scheme to determine them (e.g., adaptive or self-adaptive)?}

We implemented a \textbf{2-opt} local search operator. A 2-opt move selects two indices $(i,j)$ and reverses the
segment $[i,\dots,j]$, which replaces two edges by two new edges; improving moves are accepted iteratively until
no further improvement is found or a maximum number of iterations is reached. To avoid invalid edges on sparse
instances, candidate moves are only considered if the newly introduced edges are feasible; furthermore, 2-opt is
\textbf{skipped entirely} when the instance is detected as sparse.

In the final algorithm, 2-opt is applied \textbf{only when a new global best is found}, which provided noticeable
extra improvements without dominating the runtime. The main parameters are the maximum number of 2-opt
iterations and the improvement strategy (first-improvement vs.\ best-improvement); we use best-improvement with
a fixed iteration cap. No adaptive/self-adaptive control is used.

We considered applying local search to all offspring or during initialization, but this consumed too much time and
reduced effective exploration, so the final design restricts local search to rare best-solution updates.

\subsection{Diversity promotion mechanisms}

\ReplaceMe{Did you implement a diversity promotion scheme? If yes, which one? If no, why not? Describe the mechanism you implemented. In what sense does the mechanism improve the performance of your evolutionary algorithm? Are there parameters that need to be determined? Did you use an advanced scheme to determine them?}

Yes. Diversity is promoted through the \textbf{deterministic crowding} elimination scheme. Instead of globally
keeping only the best individuals, each offspring competes with the \emph{most similar} individual in the current
population (its rival) and replaces it only if it has better fitness. Similarity is measured by \textbf{directed
	edge overlap} (computed via a successor representation), which encourages the population to maintain multiple
coexisting ``niches'' of tours.

This mechanism improves performance by \textbf{reducing premature convergence}: improvements are introduced
locally within similar solutions, while dissimilar solutions are less likely to be overwritten by a single dominant
lineage. In our implementation there are no tunable hyperparameters beyond the chosen similarity metric; we do
not use adaptive or time-varying diversity control.

\subsection{Other considerations}\label{sec_oth}

\ReplaceMe{Did you consider other items not listed above, such as elitism, multiobjective optimization strategies (e.g., island model, pareto front approximation), a parallel implementation, or other interesting computational optimizations (e.g. using advanced algorithms or data structures)? You can describe them here or add additional subsections as needed.}

We considered several additional extensions. \textbf{Explicit elitism} is not added as a separate mechanism,
because the global best is tracked and deterministic crowding already tends to preserve strong individuals; adding
extra elitism increased selection pressure and reduced diversity in preliminary tests.

We did not implement \textbf{multiobjective} or \textbf{island-model} strategies due to time/complexity constraints
and because the provided evaluation is single-objective (tour length). Likewise, we did not implement explicit
\textbf{parallelization}; however, we focused on computational optimizations that improve performance within a
single process.

The main computational optimization is \textbf{Numba acceleration} for the fitness evaluation and core helper
routines (nearest-neighbour construction, successor building, and edge-overlap computations). In addition, sparse
instances are handled explicitly via \textbf{penalized distances} for missing edges and by \textbf{skipping 2-opt}
when the graph is sparse, which avoids wasting time on infeasible or expensive local-search moves.
